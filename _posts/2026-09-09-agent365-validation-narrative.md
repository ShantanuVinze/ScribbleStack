## Executive Summary

Microsoft Agent 365 is built around three promises: **Observe, Govern, and Secure** every agent across the enterprise. This document demonstrates those promises using Microsoft Defender Advanced Hunting and the queries in the Agent Observability KQL Repository. The telemetry, tables, charts, and screenshots were captured live from a controlled Microsoft demo tenant; the underlying activity, identities, and scenarios were simulated specifically to produce the demonstration outcomes.

The narrative is organized into four acts, each answering a core operational or security question:

| Act | Question Answered | Focus |
|---|---|---|
| **Act 1 — Prove the Signal Exists** | "Can you discover agents across your environment?" | Confirming agent telemetry lands in Defender and inventorying every active agent |
| **Act 2 — See What Agents Are Doing** | "Do you know what those agents are doing, who's using them, and how they connect?" | Usage trends, top agents/users, channel breakdown, single-run trace reconstruction, tool footprints |
| **Act 3 — Operational Confidence** | Day-to-day IT health monitoring | Inference volume, run latency, and reliability — including a genuine content-safety block that is the strongest single finding of this validation |
| **Act 4 — Detect & Block** | "Can you spot sprawl, risk, or ownerless agents before they become incidents?" | Agent-to-agent chaining, autonomous execution, geographic anomalies, volume spikes, and sensitive tool-call detection |

A single simulated agent — nicknamed **"Autonomous me"** in this demo tenant — recurs throughout all four acts, and its story is deliberately built up piece by piece: first noticed as a high-volume entry in a routine inventory query, it is progressively revealed across later acts to be dominant, largely unattended, consistently failing against its own connectors, and ultimately the only agent in the tenant to trigger a genuine anomaly-spike detection. Every step of that story uses only the queries in this repository — no custom tooling or external analytics — against real telemetry generated by the simulated demo scenarios.


## Act 1 — Prove the Signal Exists

Let's open with a direct question: *"Can you discover agents across your environment? Do you know what those agents are doing, who's using them, and how they connect? Can you spot sprawl, risk, or ownerless agents before they become incidents?"* Before Agent 365 can deliver on governance, compliance, or runtime protection, it first has to answer the most basic question of all — is agent activity actually landing where security teams already work? This act uses the controlled demo tenant to confirm that agent telemetry is flowing into Microsoft Defender's `CloudAppEvents` table, and that a single Advanced Hunting query can produce an inventory of every active agent. Everything that follows in later acts — usage patterns, tool footprints, reliability, and security detection — depends on this first proof point holding true.

### Step A2 — Discover Every Agent Active in the Tenant

**Objective:** Establish, before anything else, that agent telemetry is present and queryable in Defender — with no placeholder values required.

**Description:** This query scans the last 7 days of `CloudAppEvents` for every agent-related `ActionType` (`InvokeAgent`, `InferenceCall`, and all three `ExecuteTool*` variants), extracts each agent's identity fields from the `RawEventData` JSON payload, and summarizes run counts alongside first-seen and last-seen timestamps. It requires no prior knowledge of any specific agent — it is the starting point for building a live inventory from nothing.

**Advanced Hunting Query:**

```kusto
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType in ("InvokeAgent","InferenceCall",
"ExecuteToolBySDK","ExecuteToolByGateway","ExecuteToolByMCPServer")
| extend d = parse_json(tostring(RawEventData))
| extend AgentId = coalesce(tostring(d.TargetAgentId), tostring(d.AgentId)),
AgentName = coalesce(tostring(d.TargetAgentName), tostring(d.AgentName)),
AlternateId = tostring(d.PlatformTargetAgentId),
AgentType = coalesce(tostring(d.PlatformTargetAgentType), tostring(d.PlatformAgentType))
| summarize Runs = count(),
FirstSeen = min(Timestamp),
LastSeen = max(Timestamp)
by AgentId, AgentName, AlternateId, AgentType
| order by LastSeen desc
```

**Observed Result in the Test Environment:** The query returned 31 rows spanning roughly 15 distinct agents active over the trailing 7 days, confirming telemetry is flowing from multiple platforms at once — Microsoft first-party Copilot Studio agents and Declarative Agents, a custom SDK-built agent, and a third-party Azure AI Foundry agent. The screenshot below is captured directly from the live Advanced Hunting session, showing the query exactly as executed and the resulting agent inventory table, sorted by most-recently-active agent:

![Step A2 — live Advanced Hunting query and results, showing the tenant's agent inventory over the trailing 7 days](/assets/img/posts/agent365-validation/act1-step-a2-results.png)

In a single query, this demo tenant's unified agent inventory demonstrates a consistent inventory of agents across the environment, spanning Microsoft AI platforms, SDK-enabled agents, and connected third-party platforms — with no manual reconciliation across separate admin consoles required.

### Step A1 — Verify a Specific Agent Is Emitting Telemetry

**Objective:** Confirm, for one specific agent identified above, that its runs, tool calls, and inference calls are all landing correctly and recently — the standard first check after onboarding any new agent.

**Description:** Using the `AgentId` for "Autonomous me" captured in Step A2, this query narrows the same set of agent `ActionTypes` to the last 24 hours and filters specifically for that identity across all three of its possible identity fields (`AgentId`, `TargetAgentId`, `AlternateId`), guarding against inconsistent field population between operation types.

**Advanced Hunting Query:**

```kusto
let agentIdToFind = "9e04d05a-a60d-4f1c-85e2-2df606cb1d6f";
CloudAppEvents
| where Timestamp > ago(1d)
| where ActionType in ("InvokeAgent","InferenceCall",
"ExecuteToolBySDK","ExecuteToolByGateway","ExecuteToolByMCPServer")
| extend d = parse_json(tostring(RawEventData))
| extend AgentId = tostring(d.AgentId),
TargetAgentId = tostring(d.TargetAgentId),
AlternateId = tostring(d.PlatformTargetAgentId)
| where AgentId == agentIdToFind or TargetAgentId == agentIdToFind
or AlternateId == agentIdToFind
| project Timestamp, ActionType, d
| order by Timestamp desc
```

**Observed Result in the Test Environment:** Because "Autonomous me" runs continuously and without human pacing, the row count for this query grows with every passing hour — at the time of this screenshot it had reached 1,453 spans in the trailing 24 hours (up from an initial 30 at first check earlier in the same session), reinforcing just how much unattended activity a single autonomous agent can generate. Advanced Hunting's built-in timeline visualization renders this automatically, and the expanded first row confirms the underlying `RawEventData` detail — `ActionType: ExecuteToolBySDK`, correlated to the same conversation and agent identity confirmed in Step A2:

![Step A1 — live Advanced Hunting query and results for "Autonomous me," showing the built-in timeline visualization and an expanded raw event record](/assets/img/posts/agent365-validation/act1-step-a1-results.png)

Two details from this expanded record stood out and were carried forward into later parts of this validation: the `ChannelName` field is set to `Autonomous`, and the tool-call spans carry `UserId: N/A` — both early indicators that this particular agent operates without a human actively steering each run.

Together, Steps A2 and A1 establish the foundation the rest of this validation builds on: agent telemetry is confirmed present, current, and attributable down to the individual agent and conversation level in the controlled demo environment.


## Act 2 — See What Agents Are Doing

With telemetry confirmed present and attributable, the second question comes into focus: *"Do you know what those agents are doing, who's using them, and how they connect?"* This act moves from proving the signal exists to reading it — establishing usage volume and trend, identifying the heaviest agents and users, understanding which surfaces (Teams, Outlook, web) agents are invoked from, reconstructing a single run end-to-end as a trace tree, and profiling exactly which tools two very different agents call. Together these eight queries turn a wall of raw events into an operational picture an organization can act on.

### Step B1 — Agent Run Volume Over Time

**Objective:** Establish the overall trend of agent activity across the tenant — is usage growing, shrinking, or steady?

**Description:** This query counts `InvokeAgent` runs (the true run root, not child spans) per day over a 30-day window and renders the result as a native Advanced Hunting timechart — no external BI tool required.

**Advanced Hunting Query:**

```kusto
CloudAppEvents
| where Timestamp > ago(30d)
| where ActionType == "InvokeAgent"
| summarize Runs = count() by bin(Timestamp, 1d)
| order by Timestamp asc
| render timechart
```

**Observed Result in the Test Environment:** The chart below shows consistent daily agent activity across the full 30-day window, with no zero-run days and two clear peaks — roughly 236 runs on 11 Aug and 208 on 26 Aug — demonstrating sustained simulated activity rather than a one-off test burst.

![Step B1 — 30-day agent run volume trend, rendered natively in Advanced Hunting](/assets/img/posts/agent365-validation/act2-step-b1-results.png)

### Step B2 — Top Agents by Invocation Count

**Objective:** Identify which agents are driving the most activity, and how many distinct people are behind that activity.

**Description:** This query ranks agents by 7-day run count and pairs each with a distinct-user count (`dcount` on `UserKey`), immediately surfacing the difference between an agent used broadly by many people versus one dominated by a single account.

**Advanced Hunting Query:**

```kusto
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType == "InvokeAgent"
| extend d = parse_json(tostring(RawEventData))
| extend AgentName = coalesce(tostring(d.TargetAgentName), tostring(d.TargetAgentId)),
AgentId = tostring(d.TargetAgentId)
| summarize Runs = count(), Users = dcount(tostring(d.UserKey)) by AgentName, AgentId
| top 25 by Runs desc
```

**Observed Result in the Test Environment:** "Autonomous me" leads by a wide margin — 645 runs against just 1 distinct user — roughly two-thirds of all tenant activity concentrated in a single account. By contrast, "Zava-Public-Supplier-1" shows a healthier pattern: 15 runs spread across 4 distinct users.

![Step B2 — top agents ranked by 7-day run count and distinct user count](/assets/img/posts/agent365-validation/act2-step-b2-results.png)

### Step B3 — Top Users Invoking Agents

**Objective:** Identify which human accounts are driving the most agent activity, surfacing concentration risk.

**Description:** This query flips the view from Step B2 — instead of ranking by agent, it ranks by caller, using whichever identity field (`UserId` UPN or `UserKey` object ID) is populated.

**Advanced Hunting Query:**

```kusto
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType == "InvokeAgent"
| extend d = parse_json(tostring(RawEventData))
| extend Caller = coalesce(tostring(d.UserId), tostring(d.UserKey))
| summarize Runs = count(),
Agents = dcount(tostring(d.TargetAgentId)) by Caller
| top 25 by Runs desc
```

**Observed Result in the Test Environment:** `u101@ops.zava-corp.com` is attributed as the caller behind 645 runs — matching Step B2's "Autonomous me" count almost exactly. Every other account in the tenant drove 17 runs or fewer.

![Step B3 — top human callers ranked by 7-day run count](/assets/img/posts/agent365-validation/act2-step-b3-results.png)

### Step B4 — Channel Breakdown

**Objective:** Understand which surfaces — Teams, Outlook, web, or custom channels — agents are actually being invoked from.

**Description:** This query groups 30 days of `InvokeAgent` runs by the `ChannelName` attribute, substituting `(unset)` where the field is empty.

**Advanced Hunting Query:**

```kusto
CloudAppEvents
| where Timestamp > ago(30d)
| where ActionType == "InvokeAgent"
| extend d = parse_json(tostring(RawEventData))
| extend Channel = tostring(d.ChannelName)
| summarize Runs = count() by Channel = iff(isempty(Channel), "(unset)", Channel)
| order by Runs desc
```

**Observed Result in the Test Environment:** A channel named `Autonomous` accounts for 2,951 of roughly 3,300 total 30-day runs — around 89% of all tenant activity — dwarfing recognized channels like Copilot Studio Test Pane (150), M365Copilot (58), and Microsoft Teams (17).

![Step B4 — 30-day run breakdown by channel](/assets/img/posts/agent365-validation/act2-step-b4-results.png)

### Step B5 — Reconstruct a Single Run (Trace Tree)

**Objective:** Move from aggregate statistics to a single concrete example — what exactly happens, step by step, inside one agent conversation.

**Description:** Using the `ConversationId` captured while verifying "Autonomous me" in Act 1, this query reconstructs the full parent-child span tree for one run: the root `InvokeAgent` call followed by every downstream tool invocation it triggered, in chronological order.

**Advanced Hunting Query:**

```kusto
let conversationId = "870f90a8-6a79-43ed-9fd8-0fedd056fea0";
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType in ("InvokeAgent","InferenceCall",
"ExecuteToolBySDK","ExecuteToolByGateway","ExecuteToolByMCPServer")
| extend d = parse_json(tostring(RawEventData))
| extend ConvId = coalesce(tostring(d.ConversationId),
tostring(d.CopilotEventData.ConversationId),
tostring(d.CopilotEventData.ThreadId))
| where ConvId == conversationId
| extend SpanId = tostring(d.OpId), ParentId = tostring(d.ParentId),
Tool = tostring(d.ToolName)
| project Timestamp, ActionType, SpanId, ParentId, Tool, d
| order by Timestamp asc
```

**Observed Result in the Test Environment:** One `InvokeAgent` root span fanned out, within about 12 seconds, into a sequence of tool calls spanning seven different Microsoft 365 MCP servers — Word, Me, Teams, SharePoint, OneDrive, Mail, and Calendar — every child span correctly linked back to the same `ParentId`.

![Step B5 — reconstructed parent-child span tree for a single agent conversation](/assets/img/posts/agent365-validation/act2-step-b5-results.png)

### Step C1 — Tool Usage Summary by Tool and Type

**Objective:** Build a complete inventory of every tool agents are calling tenant-wide, and how often.

**Description:** This query aggregates every `ExecuteTool*` span by tool name, tool type, and execution path, ranked by call volume — the tool-level equivalent of Step A2's agent inventory.

**Advanced Hunting Query:**

```kusto
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType startswith "ExecuteTool"
| extend d = parse_json(tostring(RawEventData))
| extend ToolName = tostring(d.ToolName), ToolType = tostring(d.ToolType),
AgentName = coalesce(tostring(d.AgentName), tostring(d.AgentId))
| summarize Calls = count() by ToolName, ToolType, Execution = ActionType
| order by Calls desc
```

**Observed Result in the Test Environment:** The same seven MCP servers seen in Step B5 dominate, each in the 1,300+ call range for their `Initialize` lifecycle step alone. Further down the list, a long tail of lower-volume tools appears — including a single call to `mcp_MailTools.SendEmailWithAttachments`, a tool name that will resurface in Act 4.

![Step C1 — tool usage summary ranked by 7-day call volume](/assets/img/posts/agent365-validation/act2-step-c1-results.png)

### Step C2 — MCP-Server Tool Calls Only

**Objective:** Isolate tool calls executed specifically through the Agent 365 gateway's MCP-server path, a common third-party extensibility surface worth reviewing separately.

**Description:** This query filters strictly to `ActionType == "ExecuteToolByMCPServer"` — distinct from the `ExecuteToolBySDK` calls seen throughout Steps B5 and C1.

**Advanced Hunting Query:**

```kusto
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType == "ExecuteToolByMCPServer"
| extend d = parse_json(tostring(RawEventData))
| extend ToolName = tostring(d.ToolName),
AgentName = coalesce(tostring(d.AgentName), tostring(d.AgentId)),
ClientIP = tostring(d.ClientIP)
| summarize Calls = count(), Agents = dcount(tostring(d.AgentId))
by ToolName
| order by Calls desc
```

**Observed Result in the Test Environment:** Zero rows — "No results found in the specified time frame." This is a genuine, useful finding rather than a gap: every MCP tool call in this tenant is instrumented under `ExecuteToolBySDK`, not `ExecuteToolByMCPServer`. Filtering on `ToolType startswith "MCP:"`, as Step C1 does, is the reliable way to find MCP activity here.

![Step C2 — confirmed empty result for the ExecuteToolByMCPServer ActionType](/assets/img/posts/agent365-validation/act2-step-c2-results.png)

### Step C3 — Tools Used by One Specific Agent

**Objective:** Profile the complete tool footprint of a single agent — useful when reviewing an agent before certification, or scoping blast radius during an incident.

**Description:** Using the `AgentId` for "Zava-Public-Supplier-1" identified in Act 1, this query lists every distinct tool that agent has called over a 30-day window, with call counts and last-used timestamps.

**Advanced Hunting Query:**

```kusto
let agentId = "eeedf4a5-70e8-46c6-9090-827d945859e7";
CloudAppEvents
| where Timestamp > ago(30d)
| where ActionType startswith "ExecuteTool"
| extend d = parse_json(tostring(RawEventData))
| where tostring(d.AgentId) == agentId
| extend ToolName = tostring(d.ToolName), ToolType = tostring(d.ToolType)
| summarize Calls = count(), LastUsed = max(Timestamp) by ToolName, ToolType
| order by Calls desc
```

**Observed Result in the Test Environment:** A single tool — `file_search.msearch` — accounts for this agent's entire 30-day tool footprint: 20 calls, last used 3 Sep 2026. A deliberate contrast to "Autonomous me": narrow, single-purpose, and spread across four human users rather than concentrated in one account.

![Step C3 — complete 30-day tool footprint for Zava-Public-Supplier-1](/assets/img/posts/agent365-validation/act2-step-c3-results.png)

Across these eight queries, a consistent pattern emerges around one agent — "Autonomous me" — that dominates run volume, user concentration, and channel share alike, while a genuine tuning finding (Step C2) demonstrates why understanding a tenant's specific instrumentation pattern matters before relying on any single query. Both threads are carried forward into the acts that follow.


## Act 3 — Operational Confidence

Beyond discovery and usage, IT teams responsible for agents day to day need the same operational signals they already expect for any other production system: is it fast enough, and is it reliable? This act applies the same `CloudAppEvents` data to inference volume, run latency, and failure analysis — the kinds of queries an IT admin could pin to a dashboard for ongoing health monitoring. One of the four queries in this act also produced the single strongest finding of the demo validation session — a content-safety block generated by a simulated scenario and captured with full forensic detail directly in Advanced Hunting.

### Step D1 — Inference-Call Volume per Agent

**Objective:** Detect agents that make disproportionately many LLM calls per run — a common early signal of an inefficient prompt loop or a misbehaving agent.

**Description:** This query counts `InferenceCall` spans (the `chat` OTel operation) per agent per day over the trailing week.

**Advanced Hunting Query:**

```kusto
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType == "InferenceCall"
| extend d = parse_json(tostring(RawEventData))
| extend AgentName = coalesce(tostring(d.AgentName), tostring(d.AgentId))
| summarize InferenceCalls = count() by AgentName, bin(Timestamp, 1d)
| order by Timestamp asc
```

**Observed Result in the Test Environment:** Eight agents show inference activity, led by "Researcher" with a single-day spike of 112 calls. Notably, "Autonomous me" — the dominant agent in every other query so far — does not appear here at all, a real tuning gap rather than an absence of activity: this query's field extraction omits the `TargetAgentName`/`TargetAgentId` fallback used elsewhere in the repository, and this particular agent's inference spans populate only the `Target*` fields.

![Step D1 — daily inference-call volume by agent](/assets/img/posts/agent365-validation/act3-step-d1-results.png)

### Step D2 — Run Duration (Latency) per Agent

**Objective:** Establish baseline end-to-end latency per agent for performance monitoring and SLO tracking.

**Description:** This query derives each run's duration from the difference between its `CreationTime` and `CompletionTime` fields, then summarizes p50, p95, and maximum duration per agent.

**Advanced Hunting Query:**

```kusto
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType == "InvokeAgent"
| extend d = parse_json(tostring(RawEventData))
| extend StartT = todatetime(d.CreationTime),
EndT = todatetime(d.CompletionTime),
AgentName = coalesce(tostring(d.TargetAgentName), tostring(d.TargetAgentId))
| extend DurationMs = datetime_diff('millisecond', EndT, StartT)
| where isnotnull(DurationMs)
| summarize runs = count(),
p50 = percentile(DurationMs, 50),
p95 = percentile(DurationMs, 95),
maxMs = max(DurationMs) by AgentName
| order by p95 desc
```

**Observed Result in the Test Environment:** Ten agents report valid duration data. "Researcher" stands out with a p95 of roughly 422 seconds (about 7 minutes) — worth reviewing to determine whether that reflects expected deep-research behavior or a genuine performance concern. As in Step D1, "Autonomous me" is again absent, here because its spans appear to be missing a populated `CompletionTime`.

![Step D2 — run-duration percentiles (p50/p95/max) by agent](/assets/img/posts/agent365-validation/act3-step-d2-results.png)

### Step E1 — Failed Agent Runs by Error Type

**Objective:** Surface which agents are failing, and why — the standard reliability-triage starting point.

**Description:** This query filters `InvokeAgent` runs down to those where an `ErrorType` or `ErrorMessage` field is populated, summarizing failure counts per agent and error type with one example message retained per group.

**Advanced Hunting Query:**

```kusto
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType == "InvokeAgent"
| extend d = parse_json(tostring(RawEventData))
| extend ErrType = tostring(d.ErrorType), ErrMsg = tostring(d.ErrorMessage),
AgentName = coalesce(tostring(d.TargetAgentName), tostring(d.TargetAgentId))
| where isnotempty(ErrType) or isnotempty(ErrMsg)
| summarize Failures = count(), Example = any(ErrMsg) by AgentName, ErrType
| order by Failures desc
```

**Observed Result in the Test Environment:** One row — 11 `Error`-type failures on "Zava-Public-Supplier-1" — but the content behind that row is the strongest single finding of this entire validation. Expanding the record reveals a full Microsoft content-safety verdict attached directly to the span:

![Step E1 — failed-run summary showing 11 errors on Zava-Public-Supplier-1](/assets/img/posts/agent365-validation/act3-step-e1-results.png)

Drilling into the underlying event confirms the completion was **blocked** (`"blocked": true`, `"source_type": "completion"`), with the content-filter results showing Microsoft's personally-identifiable-information detector triggered on the response — flagging a **US Social Security Number, a phone number, and a physical address**, each individually marked `detected: true, redacted: true`:

![Step E1 detail — expanded content-safety record showing a blocked completion with PII detection](/assets/img/posts/agent365-validation/act3-step-e1-detail.png)

This simulated scenario demonstrates policy-based runtime protection: a third-party agent attempted to return generated sensitive personal data, the platform blocked it, and every detail of that decision — what was detected, what was redacted, and which policy engine evaluated it — is captured in `CloudAppEvents`, queryable alongside every other agent signal in this validation.

### Step E2 — Tool-Execution Failures

**Objective:** Isolate which specific tool calls are failing, to identify a flaky downstream connector, API, or MCP server.

**Description:** This query filters `ExecuteTool*` spans down to those with a non-empty `ErrorMessage`, grouped by tool, execution path, and agent.

**Advanced Hunting Query:**

```kusto
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType startswith "ExecuteTool"
| extend d = parse_json(tostring(RawEventData))
| extend ErrMsg = tostring(d.ErrorMessage), ToolName = tostring(d.ToolName),
AgentName = coalesce(tostring(d.AgentName), tostring(d.AgentId))
| where isnotempty(ErrMsg)
| summarize Failures = count(), Example = any(ErrMsg)
by ToolName, Execution = ActionType, AgentName
| order by Failures desc
```

**Observed Result in the Test Environment:** 8 rows, 130 total failures. 129 of those belong to "Autonomous me," spread uniformly as HTTP 404 (NotFound) errors across all seven of its MCP connectors — a consistent pattern pointing to a connector-configuration issue rather than random flakiness. The remaining single failure belongs to "RS_SOC_Agent," attempting `mcp_MailTools.SendEmailWithAttachments` — the same rare tool call flagged back in Step C1.

![Step E2 — tool-execution failure summary by tool, agent, and execution path](/assets/img/posts/agent365-validation/act3-step-e2-results.png)

Two threads carry forward from this act: "Autonomous me"'s uniform connector failures add a concrete reliability angle to its ongoing story, and the one failed attempt to send an email with attachments sets up the final security query in Act 4.


## Act 4 — Detect & Block

Every earlier act builds toward this one. `CloudAppEvents` is a Defender security table, which means agent telemetry can be hunted exactly like any other identity activity. This act asks: *"Can you spot sprawl, risk, or ownerless agents before they become incidents?"* The five queries here check for agent-to-agent chaining, unattended/autonomous execution, unusual source geography, abnormal volume spikes, and high-impact tool calls. Several of these queries also resolve threads deliberately left open in Acts 1–3 — turning what looked like scattered observations into a single, coherent security story.

### Step F1 — Agent-to-Agent (A2A) Calls

**Objective:** Identify agents invoking other agents, since A2A chains expand blast radius and can obscure the original human behind a request.

**Description:** This query looks for `InvokeAgent` runs where `ExecutionType == "Agent2Agent"`, or where an `AgentBlueprintId` (potential caller-agent identity) is populated.

**Advanced Hunting Query:**

```kusto
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType == "InvokeAgent"
| extend d = parse_json(tostring(RawEventData))
| extend CallerAgent = tostring(d.AgentBlueprintId),
TargetAgent = coalesce(tostring(d.TargetAgentName), tostring(d.TargetAgentId)),
ExecType = tostring(d.ExecutionType)
| where ExecType == "Agent2Agent" or isnotempty(CallerAgent)
| summarize Calls = count() by CallerAgent, TargetAgent, ExecType
| order by Calls desc
```

**Observed Result in the Test Environment:** 14 rows returned, but none with `ExecType == "Agent2Agent"` — every row's `CallerAgent` field is the all-zero placeholder GUID, meaning no genuine agent-to-agent chaining exists in this tenant today. The `ExecType` column does split cleanly, though, between `HumanToAgent` and a blank value — and "Autonomous me" is the largest contributor to that blank group, at 646 calls.

![Step F1 — agent-to-agent call analysis, showing no true A2A chains but a clear HumanToAgent vs. blank ExecType split](/assets/img/posts/agent365-validation/act4-step-f1-results.png)

### Step F2 — Autonomous (No Human Caller) Agent Runs

**Objective:** Identify runs with no traceable owning account — the real risk case, since an agent with no accountable identity behind it is much harder to investigate or restrict when something goes wrong.

**Description:** This query filters `InvokeAgent` runs to those where `UserKey` is empty, or `ExecutionType == "EventToAgent"` — in other words, it looks for **ownerless** automation, not simply "unattended" automation.

**Advanced Hunting Query:**

```kusto
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType == "InvokeAgent"
| extend d = parse_json(tostring(RawEventData))
| extend Caller = tostring(d.UserKey), ExecType = tostring(d.ExecutionType),
AgentName = coalesce(tostring(d.TargetAgentName), tostring(d.TargetAgentId))
| where isempty(Caller) or ExecType == "EventToAgent"
| summarize Runs = count(), Channels = make_set(tostring(d.ChannelName))
by AgentName, ExecType
| order by Runs desc
```

**Observed Result in the Test Environment:** Zero rows — "No results found in the specified time frame."

![Step F2 — confirmed empty result for the ownerless-agent detection logic](/assets/img/posts/agent365-validation/act4-step-f2-results.png)

At first glance this looks like it should have caught "Autonomous me" — its `ChannelName` is literally `Autonomous`, and its `ExecutionType` is blank rather than `HumanToAgent`. Pulling the raw record for one of its runs confirms why F2 didn't catch it:

```kusto
let conversationId = "870f90a8-6a79-43ed-9fd8-0fedd056fea0";
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType == "InvokeAgent"
| extend d = parse_json(tostring(RawEventData))
| where tostring(d.ConversationId) == conversationId
| extend AgentId = tostring(d.AgentId),
UserKey = tostring(d.UserKey),
UserId = tostring(d.UserId),
ChannelName = tostring(d.ChannelName),
ExecutionType = tostring(d.ExecutionType)
| project Timestamp, AgentId, UserKey, UserId, ChannelName, ExecutionType
```

![Step F2 detail — one raw InvokeAgent record for "Autonomous me," showing ChannelName "Autonomous" alongside a populated UserKey and UserId](/assets/img/posts/agent365-validation/act4-step-f2-detail-single-run.png)

`UserKey` (`b8c6f5e7-194d-40d9-…`) and `UserId` (`u101@ops.zava-corp.com`) are both filled in — not empty, not a placeholder. To confirm this isn't a one-off coincidence, the same check was run across every run of this agent over 14 days:

```kusto
CloudAppEvents
| where Timestamp > ago(14d)
| where ActionType == "InvokeAgent"
| extend d = parse_json(tostring(RawEventData))
| where tostring(d.TargetAgentId) == "9e04d05a-a60d-4f1c-85e2-2df606cb1d6f"
| extend UserKey = tostring(d.UserKey), UserId = tostring(d.UserId),
ChannelName = tostring(d.ChannelName)
| summarize Runs = count(), Example = any(Timestamp) by UserKey, UserId, ChannelName
| order by Runs desc
```

![Step F2 detail — every one of 1,534 runs of "Autonomous me" over 14 days maps to the exact same UserKey, UserId, and ChannelName](/assets/img/posts/agent365-validation/act4-step-f2-detail-1534runs.png)

All 1,534 runs collapse to a single row: same `UserKey`, same `UserId`, same `ChannelName`, every time — not a coincidence or a backfilled placeholder, but a stable, consistently configured account.

That distinction matters. `ChannelName` and `ExecutionType` answer *"was a human actively driving this specific run?"* — no, this is scheduled/event-triggered automation. `UserKey` answers a different question: *"is there an identifiable, accountable owner behind this automation?"* — yes, consistently. F2 is built to catch the second case — ownerless agents, the ones nobody could trace back to an owner if they misbehaved — and it correctly reports none, because "Autonomous me" isn't ownerless. It's autonomous in behavior but fully accountable to `u101@ops.zava-corp.com`.

**The real takeaway:** "unattended" and "ownerless" are not the same thing, and this demo tenant demonstrates the good outcome — a scheduled agent that still carries a traceable, consistent owning identity on every run. Verifying that distinction requires reading `ChannelName`/`ExecutionType` together with `UserKey`, not relying on any single field in isolation.

### Step F3 — Agent Activity from Uncommon IPs or Geographies

**Objective:** Detect agents being invoked from IP addresses or countries that are unusual for the tenant — a signal of compromised credentials or unexpected access.

**Description:** This query summarizes `InvokeAgent` runs by client IP, country, and city, then filters to source IPs seen fewer than 5 times in the trailing 7 days.

**Advanced Hunting Query:**

```kusto
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType == "InvokeAgent"
| extend d = parse_json(tostring(RawEventData))
| extend ClientIP = tostring(d.ClientIP),
AgentName = coalesce(tostring(d.TargetAgentName), tostring(d.TargetAgentId))
| where isnotempty(ClientIP) and ClientIP != "0.0.0.0"
| summarize Runs = count(), Agents = make_set(AgentName, 10),
FirstSeen = min(Timestamp), LastSeen = max(Timestamp)
by ClientIP, CountryCode, City
| where Runs < 5 // rare source IPs; tune threshold to your tenant
| order by LastSeen desc
```

**Observed Result in the Test Environment:** Seven rare source IPs spanning five countries — Ireland, the Netherlands, Poland, India, and France. "Autonomous me" is correctly excluded by the `Runs < 5` threshold, since its single, consistent source IP is high-volume and therefore not "rare" — confirming the threshold is isolating genuinely low-frequency access rather than re-flagging an agent already well understood.

![Step F3 — rare source-IP activity across five countries in the trailing 7 days](/assets/img/posts/agent365-validation/act4-step-f3-results.png)

### Step F4 — Per-Agent Run Spikes (Possible Abuse or Runaway)

**Objective:** Catch runaway loops, abuse, or misconfiguration by flagging any agent whose hourly run rate spikes well above its own baseline.

**Description:** This query bins runs per agent per hour, computes each agent's average and peak hourly volume over 14 days, and flags any agent whose peak is at least 3x its average (with a floor of 20 runs in the peak hour, to avoid flagging noise from very low-volume agents).

**Advanced Hunting Query:**

```kusto
CloudAppEvents
| where Timestamp > ago(14d)
| where ActionType == "InvokeAgent"
| extend d = parse_json(tostring(RawEventData))
| extend AgentName = coalesce(tostring(d.TargetAgentName), tostring(d.TargetAgentId))
| summarize Runs = count() by AgentName, bin(Timestamp, 1h)
| summarize avgHourly = avg(Runs), maxHourly = max(Runs),
peakAt = arg_max(Runs, Timestamp) by AgentName
| extend spikeRatio = round(todouble(maxHourly) / (avgHourly + 1), 1)
| where spikeRatio >= 3 and maxHourly >= 20
| order by spikeRatio desc
```

**Observed Result in the Test Environment:** Exactly one match — "Autonomous me," averaging 4.5 runs per hour but peaking at 34 runs in a single hour on 27 Aug 2026, a 6.1x spike over its own baseline.

![Step F4 — the only agent in the tenant to trigger the anomaly-spike detector, at 6.1x its baseline](/assets/img/posts/agent365-validation/act4-step-f4-results.png)

This is the capstone finding for "Autonomous me"'s story across the whole session: an agent first identified in a routine inventory query (Step A2) turned out to dominate tenant-wide volume, exhibit every characteristic of unattended execution, fail consistently against its own connectors, and — finally — trip a genuine, out-of-the-box anomaly detector. Every step of that story was built using nothing but the queries in this repository.

### Step F5 — Sensitive Tool Calls (Delete / Send / External)

**Objective:** Continuously monitor for agent tool calls with real-world side effects — deleting data, sending messages, or reaching external systems.

**Description:** This query matches `ToolName` against a regular expression covering common high-impact verbs (delete, remove, send, purge, share, grant, invoke, external, payment, transfer). The source repository's version of this query (below, unmodified) projects one row per matching event, ordered by time — useful for a scrolling live feed of sensitive tool calls.

**Advanced Hunting Query (source repository, as published):**

```kusto
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType startswith "ExecuteTool"
| extend d = parse_json(tostring(RawEventData))
| extend ToolName = tostring(d.ToolName), ToolType = tostring(d.ToolType),
AgentName = coalesce(tostring(d.AgentName), tostring(d.AgentId)),
Caller = coalesce(tostring(d.UserId), tostring(d.UserKey))
| where ToolName matches regex @"(?i)(delete|remove|send|purge|share|grant|invoke|external|payment|transfer)"
| project Timestamp, AgentName, ToolName, ToolType, Execution = ActionType, Caller
| order by Timestamp desc
```

**Query variant actually run for this result (summarized for clarity):** Because the raw, row-per-event query above returned 91 individual rows in the test tenant, it was summarized by `ToolName` for this session so the false-positive pattern is visible in a single screenshot rather than requiring a scroll through 91 rows:

```kusto
CloudAppEvents
| where Timestamp > ago(7d)
| where ActionType startswith "ExecuteTool"
| extend d = parse_json(tostring(RawEventData))
| extend ToolName = tostring(d.ToolName)
| where ToolName matches regex @"(?i)(delete|remove|send|purge|share|grant|invoke|external|payment|transfer)"
| summarize Calls = count() by ToolName
| order by Calls desc
```

**Observed Result in the Test Environment:** The 91 raw matching rows collapse to just 4 distinct tools. Two of them — `mcp_SharePointRemoteServer` (1,991 calls) and `SharepointSiteSearch` (9 calls) — are false positives, matching only because the word "SharePoint" contains "share." The one genuine hit is `mcp_MailTools.SendEmailWithAttachments`, matching on "send" — a single call, and the same tool flagged as rare back in Step C1 and confirmed to have failed in Step E2. The screenshot below reflects the summarized variant above, not the row-per-event original.

![Step F5 — sensitive-tool regex results (summarized variant), showing connector-name false positives alongside the one genuine "send" match](/assets/img/posts/agent365-validation/act4-step-f5-results.png)

This closes the loop opened two acts earlier: a sensitive action (sending email with attachments) was attempted, it failed, and this query — once tuned to exclude connector-name noise — is exactly how a security team would find it. The false-positive volume is itself a useful, tenant-specific finding: filtering purely on substrings of a tool's display name is not enough when a legitimate connector name happens to contain a sensitive verb.

Across all five queries, this act demonstrates through real telemetry generated in the controlled demo tenant that Defender does not just observe agent activity — it can detect agent-to-agent chaining (or its absence), unattended execution, geographic anomalies, volume spikes, and high-impact tool calls, all from the same table used throughout this validation.
